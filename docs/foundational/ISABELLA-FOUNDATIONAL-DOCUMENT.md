### 9.5 Capability Gateway

El Capability Gateway es el punto de entrada central del C.R.O.W.N. Recibe una `CapabilityRequest`, resuelve qué Skill provee esa capacidad, valida permisos contra la federación, registra la operación en BookPI, y devuelve un `CapabilityResponse` normalizado.

```typescript
interface CapabilityRequest {
  capability: string;        // "memory.store" | "execution.run" | "knowledge.query" | ...
  payload: unknown;
  federationId: FederationId;
  traceId: string;
  hexagonId: string;
}

interface CapabilityResponse<T = unknown> {
  ok: boolean;
  data?: T;
  error?: string;
  traceId: string;
  bookpi: { nodeId: string; hash: string; timestamp: number };
}
```

### 9.6 Reglas de Eficiencia, Tipo y Telemetría

Cada Skill que pasa por el Capability Gateway debe cumplir:

- **Eficiencia:** Operaciones O(n), sin allocaciones innecesarias, sin sorts sobre colecciones completas.
- **Tipo:** Input y output definidos con Zod (TS) o DTOs (PHP). Sin `any`. Sin payloads sin esquema.
- **Telemetría:** Cada llamada genera `traceId` único, identificación de `hexagonId` (interior: identity/kernel/memory/governance/audit; exterior: interoperability/signal/territorial), y `federationId`. Todo se registra en BookPI.

### 10.3 Provider Failover

Isabella no depende de un solo proveedor de modelos. El Provider Failover orquesta la disponibilidad:

```
Priority 1: Anthropic (Claude)
Priority 2: OpenAI (GPT-4o)
Priority 3: DeepSeek
Priority 4: Otros proveedores
```

**Reglas:**
- Solo acepta salidas que cumplen el Zod schema del agente solicitante.
- Si un proveedor falla, intenta el siguiente automáticamente.
- Si todos fallan, devuelve error canónico con traza completa.
- Cada intento se registra en BookPI con su propio `traceId`.

### 10.4 Sistema de Errores Canónicos

**TypeScript:**
```typescript
class TAMVKernelError extends Error {
  code: string;          // "KERNEL_AUTH_FAILED" | "KERNEL_SCHEMA_INVALID" | ...

  trace: string[];
}
```

**PHP:**
```php
class TAMVKernelException extends \Exception {
    public string $code;
    public int $httpStatus;
    public array $metadata;
    public array $trace;

```

### 10.5 BookPI Telemetry Middleware

Toda operación que pase por el K5 Kernel se registra en BookPI:

```
Request → Extract traceId/hexagon/federationId → Sign with SHA-256 →
Store in BookPI Ledger → Forward to handler → Sign response →
Store in BookPI Ledger → Return
```

En Bun/TS: `withBookPiTelemetry` middleware HTTP.
En Laravel: `BookPITelemetry` middleware en routes y jobs.

## 14. MEXA API — CRIPTOGRAFÍA DE SOBERANÍA

### 14.1 Definición

**Mexa API** es la capa de criptografía de soberanía de Isabella, diseñada por Edwin Castillo Trejo. Proporciona identidad criptográfica, firma de payloads y verificación de procedencia para las 7 federaciones.

### 14.2 Componentes

#### Federation Mask
- Firma SHA-256 sobre `{federationId}:{nodeId}:{timestamp}:{secret}`
- Expiración temporal: 5 minutos (300,000ms)
- Validación: federation ID debe ser uno de los 7 conocidos

#### Payload Signing
- Combinación: `JSON(payload) + federationMask.signature + randomNonce`
- Firma: SHA-256 del resultado
- Output: `SignedPayload { payload, federationMask, hash, nonce }`

#### Verification
- Re-derivación del hash y comparación
- Validación de expiración temporal
- Output: `VerificationResult { valid, federation, node, reason? }`

### 14.3 Propósito

Mexa API no es un servicio de autenticación genérico. Es un **sistema de atribución criptográfica** que garantiza que cada operación de Isabella pueda ser rastreada hasta su federación y nodo de origen, con verificación de integridad y vigencia temporal.

## 18. DEBILIDADES

### 18.1 Reconocidas
1. **Sin modelo propio de lenguaje:** El "cerebro" real depende del modelo orquestado (Anthropic, OpenAI, DeepSeek). Sin esas APIs, Isabella opera con regex + templates.
2. **Clasificador regex:** El Intention Parser usa patrones regulares, no un modelo de ML entrenado.
3. **Personalidad post-procesamiento:** Las reglas 3S son transformaciones de texto, no comportamiento emergente del modelo.
4. **Memoria in-memory actual:** La mayoría de los módulos operan con estado en memoria. Falta persistencia real en DB.
5. **PQC stubs:** Las firmas Dilithium y Kyber son implementaciones mock, no criptografía real.
6. **Escala territorial:** Diseñada para un territorio (Real del Monte), no para millones de usuarios concurrentes.
7. **Knowledge base limitada:** 19 entradas de conocimiento TAMV. Falta expansión masiva.
8. **Sin fine-tuning:** No hay modelo entrenado específicamente para el dominio TAMV.
9. **Dependencia de DB:** Los módulos Genesis/Federation están diseñados para Supabase pero aún operan in-memory.
10. **Sin tests unitarios formales:** La cobertura de tests es baja.

### 18.2 Mitigaciones Planificadas
- **Provider Failover** mitiga la dependencia de un solo modelo.
- **Memory Fabric** mitiga la pérdida de estado al reiniciar.
- **Knowledge Fabric** mitiga la limitación de conocimiento.
- **Multi-Agent Collective** mitiga las limitaciones del razonamiento regex.
- **Self-Evaluation Engine** mitiga la falta de fine-tuning.
